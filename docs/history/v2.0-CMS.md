# HaxePress 2.0.0 acceptance record

HaxePress is a general-purpose CMS built on HxWell, Crossbyte, SQLite and Inertia/React. English is the default language; Turkish catalogues are included. Earlier implementation and API 2 verification records are retained in [the historical ledger](history/v1-CMS.md).

## Naming and application boundary

All repository-owned application classes live below `hx.press`: services, controllers, handlers, models, providers, configuration, routes, packages, plugins, migrations and translations. Framework imports retain `hx.well.*`; Java externs retain the runtime namespaces required by their bindings. Haxe calls use explicit imports and short type names.

The generic domain vocabulary is Content, Pages, Media, Categories and Tags. `ContentItem` stores entries/pages in `content_items`, distinguished by `content_type = entry | page`; tag relations use `ContentTag`, `content_tags` and `content_id`. Inertia pages are `Home`, `ContentIndex`, `ContentDetail`, `Page`, `About` and `NotFound`. Canonical routes are `/content`, `/content/{slug}`, `/pages/{slug}`, `/tags/{slug}` and `/admin/content`.

Configuration discovery uses `hxwell_config_package=hx.press.config` before library options in the compiler configuration. The project-local `hxwell-config-package.patch` supports application configuration overrides while preserving framework defaults. It reverses and reapplies exactly. Setup applies it without modifying sibling checkouts or global Haxelib registrations.

## Data and compatibility

The naming migration uses native Schema/model APIs. It renames the existing content and tag tables, reference column and core indexes; preserves record IDs, content and relationships; and normalizes legacy content types, revision snapshots and private working-copy keys. Conflicting old/new tables or working-copy keys cause a visible startup error while retaining both copies. Migration batches are bounded.

Known factory site labels are changed to HaxePress and generic CMS copy. Custom editorial content and custom site settings remain intact. Legacy public URLs redirect permanently to canonical paths, retaining query parameters. Protected legacy content-list/editor GET URLs redirect inside the administration route group.

CMS 2.0.0 uses plugin/theme API 3. Native plugins and renderer themes built against older application namespaces, models or page contracts require a rebuild. Matching bundled packages upgrade before plugin startup and preserve settings, activation, selected theme and plugin-owned data/migration history. The SDK and version-specific ZIPs contain JAR, CPPIA and PHP artifacts.

## Existing capabilities retained

Content/page editing includes Markdown/GFM, uploaded images, SEO fields, scheduled publication, trash/restore, private working copies, stale-save protection and bounded revision history. Media, categories, tags, navigation, roles/capabilities and activity management remain available. Administration uses the explicit `admin` guard and its own sessions; public requests remain session-free.

Simple remains the minimal default theme. Fieldnotes, Notebook and Gallery are separate theme packages. Theme preview uses an isolated frame with desktop/tablet/mobile controls. The administration design uses its own navy navigation and local IBM Plex Sans assets.

RSS, Newsletter and Reading Companion remain native plugins. Lifecycle callbacks own routes and report creation/destruction failures with a process-restart warning. Plugin database APIs retain native models/Schema, named migrations, scoped JSON values, alternate connections and data retention across disable/uninstall/reinstall. Storage operations use configured disks and bounded streams.

Queries filter, count, sort and limit in the database. Lists omit content bodies and use cursor pagination; reading time is write-time metadata. Caches store specific query results as typed plain records. Application and test source contain no raw SQL or direct filesystem access in Haxe; framework compatibility patches own necessary statement generation.
